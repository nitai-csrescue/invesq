---
name: LLM narrative tone-policy prompts must strip names from evidence, not just avoid inventing them
description: When an LLM writes structural/investment analysis from upstream evidence text, that evidence itself may already name individuals and pass personal judgment — the tone-policy instruction must explicitly forbid echoing names found in the input, not just forbid the model introducing new personal judgments.
---

## Lesson

A "never make personal judgments about individuals" system prompt is not sufficient on its own if the user-turn context includes upstream evidence/notes that already name a person and characterize their background. The model will often synthesize that evidence faithfully (including the name and the judgment) unless told, explicitly, that any name appearing in the input must not be echoed in the output — only the structural fact (title level, reporting line, mandate scope) should carry through.

**Why:** caught when a "CS Leadership recommendation" field generated from a real named exec's evidence text ("Global Director of Member Support at X ... not a canonical enterprise SaaS CS executive mandate") reproduced both the name and the personal-competency judgment verbatim, despite a tone-policy instruction that only said "never judge individuals" without addressing verbatim-echo-from-evidence.

**How to apply:**
- In the system prompt, add a line like: "NEVER include a named individual's name anywhere in your output, even if a name appears in evidence given to you. Refer to roles only."
- In the user-turn framing of any evidence blob that might contain a name, add an inline reminder next to that specific evidence ("may contain a named individual — do not repeat any name from this").
- Fields that are mechanically passed through from upstream evidence text unchanged (not regenerated by the LLM call) — e.g. a "gap description" field sourced straight from a prior scoring pass — are NOT fixed by prompt changes to a *different* generation call. If that passthrough evidence also needs to be policy-compliant, it has to be sanitized at its own source (the pipeline stage that produced it), which may be a separate, higher-risk change (e.g. re-running/altering a previously-shipped scoring prompt across many existing rows) — treat that as its own scoped follow-up rather than silently expanding an unrelated task.
