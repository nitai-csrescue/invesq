### Step 5 — Root cause and pipeline guard

**Root cause (confirmed in prior diagnostic entry):** `scoreAndPersistCompany()` in `artifacts/api-server/src/lib/jobs/build.ts` performs an unconditional `db.insert(assessmentsTable)` with no check for an existing `(companyId, date)` row. Four build jobs ran against firm 1 on 2026-07-10 (ids 2, 3, 4 within a 9-minute window, id 5 ~18.5 hours later), each independently scoring and inserting a new assessment for all 5 active companies — producing 4 rows per company for the same calendar date. Discovery's company-insert similarly lacked within-run dedup, producing the duplicate ClarisHealth company row.

**Pipeline guard status after Publish 2:** The `assessments_company_date_uq` unique index IS the guard for assessments — a repeated build run will now error at the INSERT instead of silently duplicating. However, the pipeline does not currently handle that insert error gracefully: `scoreAndPersistCompany()` will throw, the build job will be marked `"failed"`, and assessments already written for earlier companies in the loop are kept (they're independent Postgres writes). This is acceptable behavior (fail loudly, no silent duplication) but is not a true upsert or skip-if-exists. **Recommendation (unimplemented, noted for Phase 5):** `scoreAndPersistCompany()` should explicitly check for an existing row at `(companyId, todayIso())` before scoring, either skipping or replacing with a deliberate re-score semantics. This prevents a failed-job scenario if a pipeline run needs to be retried on the same calendar day. The unique index provides the production guard; the graceful-handling question is deferred to Phase 5 scope.

For the discovery duplicate-company issue: the `companies_firm_normalized_name_active_uq` partial index similarly becomes the guard after Publish 2. Same graceful-handling note applies.
